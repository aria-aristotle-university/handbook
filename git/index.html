Αυτός ο οδηγός σού μαθαίνει πώς δουλεύουμε μαζί στον κώδικα και στα αρχεία της ARIA. Δεν χρειάζεται να έχεις ξαναδεί git ή GitHub. Δεν χρειάζεται καν να γράφεις κώδικα.

Τι θέλουμε να σου μείνει

Σήμερα ένα LLM (ChatGPT, Claude, Gemini κ.ά.) σού δίνει όποια εντολή git χρειαστείς σε λίγα δευτερόλεπτα. Ορισμένα εργαλεία AI μπορούν και να την τρέξουν για σένα. Γι' αυτό δεν χρειάζεται να αποστηθίσεις εντολές, ούτε καν να τις γράφεις.

Αυτό που δεν μπορεί να κάνει για σένα είναι να έχει την εικόνα στο μυαλό σου: τι συμβαίνει κάθε στιγμή. Σε ποιο branch είσαι, τι υπάρχει στον υπολογιστή σου και τι στο GitHub, τι θα αλλάξει αν πατήσεις ένα κουμπί. Με αυτή την εικόνα ξέρεις τι να ζητήσεις, και καταλαβαίνεις αν η απάντηση που πήρες είναι σωστή.

Γι' αυτό ο οδηγός εστιάζει στις ιδέες και στα διαδραστικά. Οι εντολές είναι εκεί για όταν τις χρειαστείς.

Τι θα μάθεις

  • Τι είναι το git και τι είναι το GitHub, και γιατί είναι δύο διαφορετικά πράγματα.
  • Πού βρίσκεται το repo της υποομάδας σου και πού μπορείς να γράψεις.
  • Πώς στήνεις τον υπολογιστή σου μία φορά, σωστά.
  • Τον καθημερινό κύκλο της ARIA: παίρνεις μια εργασία, φτιάχνεις branch, κάνεις αλλαγές, τις στέλνεις για έλεγχο και μπαίνουν στην επίσημη έκδοση.
  • Τι κάνεις όταν δύο άτομα αλλάξουν το ίδιο αρχείο.
  • Ποια αρχεία ανεβαίνουν στο GitHub και ποια ποτέ.
  • Πώς διορθώνεις τα συνηθισμένα λάθη χωρίς πανικό.

Πόσο θα σου πάρει

  • Περίπου 40 λεπτά για τα κεφάλαια 0 έως 8, μαζί με τα διαδραστικά. Αυτό είναι το κύριο διάβασμα.

  • 15 λεπτά για την τελική άσκηση: το πρώτο σου πραγματικό Pull Request. Μην την παραλείψεις.
  • Το κεφάλαιο "Για προχωρημένους" είναι προαιρετικό. Το διαβάζεις όταν το χρειαστείς.

Πώς να το διαβάσεις

  • Μην ξεχάσεις το κεφάλαιο 11. Αφού τελειώσεις το 8, κάνε την πρώτη σου συνεισφορά: εκεί ανεβάζεις το πρώτο σου πραγματικό Pull Request.

0. Γιατί τα χρειαζόμαστε όλα αυτά

Αυτό το κεφάλαιο δείχνει το πρόβλημα που λύνει το git, πριν μάθεις οποιαδήποτε νέα λέξη.

Κοίτα αυτόν τον φάκελο. Τον έχεις δει κι εσύ κάπου.

Τώρα απάντησε σε τρεις ερωτήσεις:

  • Ποιο αρχείο είναι το σωστό; Ποιο έτρεξε στο τελευταίο test του βραχίονα;
  • Ποιος άλλαξε τι, και γιατί; Κάποιος μείωσε την ταχύτητα των αρθρώσεων. Ποιος; Για ποιο λόγο;
  • Τι γίνεται αν δύο άτομα αλλάξουν το ίδιο αρχείο την ίδια μέρα; Συνήθως ο ένας σβήνει τη δουλειά του άλλου χωρίς να το καταλάβει.

Ένα παράδειγμα που θα συμβεί σίγουρα

  • Δευτέρα πρωί. Η Μαρία και ο Νίκος κατεβάζουν από το Drive το ίδιο αρχείο, το ik_solver.py.
  • Δευτέρα μεσημέρι. Η Μαρία προσθέτει έλεγχο στα όρια των αρθρώσεων. Ο Νίκος, στο δικό του αντίγραφο, αλλάζει την ταχύτητα. Ο καθένας ανεβάζει το δικό του αρχείο.
  • Δευτέρα βράδυ. Ο Νίκος ανέβασε τελευταίος, οπότε το αρχείο του αντικατέστησε της Μαρίας. Η δουλειά της Μαρίας χάθηκε, και κανείς δεν το έχει καταλάβει.

Με δύο άτομα αυτό συμβαίνει πού και πού. Με πέντε άτομα στο ίδιο repo συμβαίνει κάθε βδομάδα. Και όσο περνάει ο καιρός, τα αντίγραφα και οι αλλαγές πολλαπλασιάζονται, ώσπου κανείς δεν ξέρει πια ποια έκδοση είναι η «αληθινή».

Σε μια ομάδα με 55 μέλη και δύο ρομπότ, αυτό γίνεται χάος πολύ γρήγορα.

Συμβουλή

Καλά νέα: δεν θα ξαναδείς ποτέ αρχείο με όνομα final_v2. Ένα αρχείο, ένα όνομα, και όλο το ιστορικό του κρυμμένο από πίσω.

01· GIT ΚΑΙ GITHUB

1. git και GitHub: η μεγάλη εικόνα

Αυτό το κεφάλαιο ξεχωρίζει τα δύο εργαλεία που θα χρησιμοποιείς: το git στον υπολογιστή σου και το GitHub στο internet.

git: τέλος στο μπέρδεμα με τις εκδόσεις.

Κάθε αρχείο έχει ένα όνομα και όλο το ιστορικό του από πίσω. Το git είναι πρόγραμμα στο laptop σου και δουλεύει χωρίς internet.

GitHub: το git της ομάδας.

Ιστότοπος που κρατάει ένα κοινό αντίγραφο του project για όλη την ομάδα. Εκεί μαζεύεται η δουλειά όλων και ελέγχεται πριν μπει στην επίσημη έκδοση.

1.1Version control: η ιδέα

Version control (έλεγχος εκδόσεων) λέμε ένα σύστημα που θυμάται κάθε αποθηκευμένη έκδοση ενός project: τι άλλαξε, ποιος το άλλαξε και γιατί.

Σκέψου το save game σε ένα βιντεοπαιχνίδι:

  • Αποθηκεύεις όταν φτάνεις σε ένα καλό σημείο.
  • Δίνεις όνομα στο save, π.χ. "πριν το boss".
  • Αν κάτι πάει στραβά, φορτώνεις το παλιό save.

Το version control κάνει το ίδιο για τα αρχεία της ομάδας. Διαφέρει από ένα απλό backup σε δύο σημεία:

  • Κάθε save έχει εξήγηση γραμμένη από άνθρωπο.
  • Επιτρέπει σε πολλούς ανθρώπους να δουλεύουν παράλληλα στο ίδιο project.

Παράδειγμα ARIA: στο repo arm-control βλέπεις ποιος άλλαξε τα PID gains και πότε. Και μπορείς να γυρίσεις στην έκδοση που δούλεψε στο τελευταίο test.

Αν έχεις δει το "Ιστορικό εκδόσεων" στα Google Docs, η ιδέα είναι παρόμοια. Η διαφορά είναι ότι εσύ αποφασίζεις πότε κρατάς έκδοση και εσύ γράφεις γιατί.

1.2git

Το git είναι ένα δωρεάν πρόγραμμα στον δικό σου υπολογιστή που κάνει version control σε έναν φάκελο.

  • Το εγκαθιστάς μία φορά.
  • Κρατάει το ιστορικό του φακέλου τοπικά, στο laptop σου.
  • Δουλεύει και χωρίς internet.

1.3GitHub

Το GitHub είναι ένας ιστότοπος που φιλοξενεί online τα project του git και προσθέτει εργαλεία για ομαδική δουλειά.

Τι προσθέτει πάνω στο git:

  • Ένα κοινό αντίγραφο του project, που βλέπει όλη η ομάδα.
  • Εργασίες με αριθμό, π.χ. "#67: διόρθωσε τα όρια του βραχίονα".
  • Έλεγχο αλλαγών πριν μπουν στην επίσημη έκδοση.
  • Δικαιώματα: ποιος βλέπει και ποιος γράφει τι.

Όλα αυτά τα εξηγούμε ένα ένα στα επόμενα κεφάλαια.

Παράδειγμα ARIA: στο github.com/aria-aristotle-university ζουν όλα τα project, οι εργασίες και οι έλεγχοι της ομάδας.

Προσοχή

Δύο παγίδες:

  • Στο GitHub δεν γράφεις τον κώδικα. Τον γράφεις στον υπολογιστή σου και τον στέλνεις στο GitHub.
  • Το GitHub της ARIA δεν είναι δημόσιο. Όλα τα project μας είναι private: τα βλέπουν μόνο τα μέλη της ARIA που έχουν πρόσβαση.

Αναλογία

Το git είναι η φωτογραφική μηχανή. Το GitHub είναι το κοινό online άλμπουμ της ομάδας.

Βγάζεις φωτογραφίες με τη μηχανή σου, όπου κι αν είσαι. Όταν θέλεις να τις δουν οι άλλοι, τις ανεβάζεις στο άλμπουμ.

2. Πού ζουν τα πράγματα: η πολυκατοικία

Αυτό το κεφάλαιο σού δείχνει πώς είναι οργανωμένη η ARIA στο GitHub, ώστε να βρίσκεις αμέσως πού δουλεύεις.

Αναλογία

Η ARIA στο GitHub είναι μια πολυκατοικία.

  • Η πολυκατοικία είναι ο οργανισμός (organization).
  • Κάθε διαμέρισμα είναι ένα repo.
  • Κάθε δωμάτιο μέσα στο διαμέρισμα είναι ένας φάκελος.

Θα συναντήσεις αυτή την εικόνα σε όλο τον οδηγό.

2.1Organization

Το organization είναι ένας λογαριασμός στο GitHub που ανήκει σε μια ομάδα. Κρατάει τα project και τα μέλη της ομάδας σε ένα μέρος.

  • Το organization της ARIA λέγεται aria-aristotle-university.
  • Βρίσκεται στο github.com/aria-aristotle-university.

Συμβουλή

Δεν χρειάζεσαι ξεχωριστό λογαριασμό "ARIA". Χρησιμοποιείς τον προσωπικό σου λογαριασμό στο GitHub. Η ομάδα σού στέλνει πρόσκληση και μπαίνεις στην πολυκατοικία με αυτόν.

2.2Repository (repo)

Το repository, ή σκέτο repo, είναι ένας φάκελος project που το git παρακολουθεί, μαζί με όλο το ιστορικό του.

Στην ARIA έχουμε ένα repo για κάθε υποομάδα κάθε ρομπότ, συν τρία κοινά.

Το repo arm-control είναι ένα διαμέρισμα. Οι φάκελοι μέσα του, π.χ. src/ και config/, είναι τα δωμάτιά του.

2.3Teams και δικαιώματα

Τα teams είναι ομάδες μελών μέσα στο organization. Κάθε team παίρνει δικαίωμα να διαβάζει ή να γράφει σε συγκεκριμένα repos.

  • Διαβάζω (read): βλέπω τα αρχεία και το ιστορικό, κατεβάζω αντίγραφο.
  • Γράφω (write): μπορώ επιπλέον να στέλνω αλλαγές και να προτείνω να μπουν στην επίσημη έκδοση.

Ο κανόνας της ARIA:

  • Διαβάζεις όλα τα repos. Βλέπεις τον κώδικα και τα αρχεία κάθε υποομάδας.
  • Γράφεις μόνο στο repo της υποομάδας σου και στο docs.

Παράδειγμα: αν είσαι στο arm-control, βλέπεις τον κώδικα του quadruped-control, αλλά δεν μπορείς να στείλεις αλλαγές εκεί. Χρειάζεσαι κάτι να αλλάξει εκεί; Μίλα με τον coordinator σου. Θα το συζητήσει με τον coordinator εκείνης της υποομάδας και θα βρείτε μαζί τη λύση.

2.4README.md και CONTRIBUTING.md

Το README.md και το CONTRIBUTING.md είναι δύο αρχεία κειμένου που βρίσκεις στην αρχική σελίδα κάθε repo.

  • README.md: τι είναι αυτό το repo και πώς το τρέχεις. Είναι η ταμπέλα στην πόρτα του διαμερίσματος.
  • CONTRIBUTING.md: πώς δουλεύουμε σε αυτό το repo. Είναι ο κανονισμός του διαμερίσματος. Εκεί υπάρχει και η λίστα με τα αρχικά των μελών, που θα χρειαστείς στο κεφάλαιο 5.

Κανόνας ARIA

Πριν φτιάξεις το πρώτο σου branch (κεφάλαιο 5), άνοιξε το CONTRIBUTING.md του repo σου. Έλεγξε ότι υπάρχουν τα αρχικά σου, π.χ. ga για τη Γεωργία Α. Αν λείπουν, ζήτα από τον coordinator να τα προσθέσει.

Το Markdown είναι ένας απλός τρόπος να μορφοποιείς κείμενο με σύμβολα. Το χρησιμοποιούν τα README, οι εργασίες και οι συζητήσεις στο GitHub.

3.1Λογαριασμός, πρόσκληση και 2FA

Ο λογαριασμός GitHub είναι η ταυτότητά σου σε όλα τα repos της ARIA.

Βήματα:

  1. Πήγαινε στο github.com και πάτα Sign up.
  2. Διάλεξε επαγγελματικό username, π.χ. georgia-antoniou ή gantoniou. Αυτό το όνομα θα το δουν η ομάδα και ίσως μελλοντικοί εργοδότες.
  3. Βάλε το αληθινό σου όνομα στο προφίλ: Settings → Public profile → Name, π.χ. Georgia Antoniou. Έτσι η ομάδα ξέρει ποιος είναι πίσω από κάθε username.
  4. Ενεργοποίησε το 2FA (two-factor authentication): Settings → Password and authentication → Enable two-factor authentication.

Προσοχή

4.10.gitignore: τι αγνοεί το git

Το .gitignore είναι ένα αρχείο μέσα στο repo με τη λίστα των αρχείων που το git αγνοεί. Είναι αρχεία που φτιάχνει μόνος του ο υπολογιστής σου (π.χ. αποτελέσματα build) ή που δεν πρέπει ποτέ να ανέβουν (π.χ. κωδικοί). Δεν εμφανίζονται στο status, οπότε δεν τα ανεβάζεις κατά λάθος.

5. Branches: παράλληλη δουλειά χωρίς χάος

Αυτό το κεφάλαιο σού δείχνει πώς δουλεύουν πολλοί άνθρωποι στο ίδιο repo χωρίς να πατάει ο ένας τη δουλειά του άλλου.

Η Γεωργία διορθώνει τον IK solver. Την ίδια εβδομάδα ο Μάνος (mk) φτιάχνει τον έλεγχο του gripper, στο ίδιο repo. Και οι δύο θέλουν να δουλέψουν χωρίς να χαλάσουν την έκδοση που τρέχει στο ρομπότ.

5.1Branch

Το branch είναι σαν ένα δικό σου αντίγραφο του κώδικα. Το αλλάζεις και το δοκιμάζεις όσο θέλεις, και τίποτα δεν χαλάει στο main, την επίσημη έκδοση που χρησιμοποιούν όλοι.

Όταν η δουλειά σου είναι έτοιμη, οι αλλαγές σου μπαίνουν πίσω στο main. Αυτό λέγεται merge. Στην ARIA γίνεται μόνο αφού τις ελέγξει ο coordinator (κεφάλαιο 7).

Στο γράφημα πάνω:

  • Η γραμμή της Γεωργίας είναι το branch 67-fix-ik-joint-limits/ga.
  • Η γραμμή του Μάνου είναι το branch 65-add-gripper-service/mk.
  • Κάθε branch έχει τα δικά του commits. Ο ένας δεν βλέπει τα commits του άλλου μέχρι να ενωθούν.

Προσοχή

Στην πράξη το git δεν αντιγράφει τα αρχεία. Ο φάκελός σου μένει ένας, και τα αρχεία μέσα του αλλάζουν όταν αλλάζεις branch (5.5).

Το όνομα του branch λέει με μια ματιά ποιος δουλεύει και σε τι.

Κανόνας ARIA

Αν αλλάξει ο τίτλος του Issue, το branch δεν μετονομάζεται. Ο αριθμός αρκεί για να βρεθεί το Issue.

5.3main: η επίσημη έκδοση

Το main είναι το επίσημο branch κάθε repo. Κρατάει πάντα την έκδοση που δουλεύει και έχει εγκριθεί.

  • Όταν φτιάχνεις ένα repo, το git ξεκινάει με ένα branch: το main.
  • Όλα τα άλλα branches ξεκινούν από το main και κάποια στιγμή επιστρέφουν σε αυτό.
  • Σε παλιά tutorials θα το δεις ως master. Είναι το ίδιο πράγμα με παλιότερο όνομα.

Κανόνας ARIA

Κανείς δεν στέλνει αλλαγές κατευθείαν στο main.

Το main είναι ο κοινός κώδικας όλης της υποομάδας. Ό,τι μπαίνει εκεί το χρησιμοποιούν όλοι, οπότε πρέπει να είμαστε σίγουροι ότι δουλεύει. Γι' αυτό κάθε αλλαγή περνάει από Pull Request και τη βλέπει και ένας δεύτερος άνθρωπος πριν μπει (review):

  • Τον κώδικα ενός μέλους τον ελέγχει ο coordinator.
  • Τον κώδικα του coordinator τον ελέγχει ένα μέλος της υποομάδας.

Τα εξηγούμε όλα στο κεφάλαιο 7.

5.4HEAD: "είσαι εδώ"

Το HEAD είναι η κουκκίδα "είσαι εδώ" του git: δείχνει σε ποιο branch και σε ποιο commit βρίσκεσαι τώρα.

  • Όταν κάνεις commit, το νέο commit μπαίνει εκεί που δείχνει το HEAD.
  • Το status σού το λέει στην πρώτη γραμμή: On branch 67-fix-ik-joint-limits/ga.
  • Στο GitHub Desktop το βλέπεις πάνω, στο Current branch.

Αναλογία

Όπως η κόκκινη τελεία "Βρίσκεστε εδώ" στον χάρτη ενός εμπορικού κέντρου.

5.5Switch: αλλαγή branch

Το switch σε μεταφέρει σε άλλο branch. Τα αρχεία στον φάκελό σου αλλάζουν ώστε να ταιριάζουν με εκείνο το branch.

Φτιάχνω νέο branch και πηγαίνω σε αυτό:

Πηγαίνω σε branch που υπάρχει ήδη:

GitHub DesktopΓραμμή εντολών

Προσοχή

"Εξαφανίστηκαν τα αρχεία μου!" Δεν εξαφανίστηκαν. Είναι ασφαλή στο άλλο branch. Γύρνα πίσω με switch και θα τα βρεις.

Πριν αλλάξεις branch, κάνε commit. Αν έχεις αλλαγές που δεν έχουν μπει σε commit, το git είτε αρνείται να αλλάξει branch είτε τις παίρνει μαζί του. Για ενδιάμεσες λύσεις δες το "stash" στο κεφάλαιο 10.

Σε tutorials θα δεις και την εντολή git checkout. Είναι η παλιά, πολυεργαλείο εντολή. Εμείς χρησιμοποιούμε git switch για branches και git restore για αρχεία (κεφάλαιο 10). Κάνουν το ίδιο, με πιο καθαρά ονόματα.

Έτσι το branch σου ξεκινάει από την πιο πρόσφατη επίσημη έκδοση.

5.7Merge: ενώνεις δύο branches

Το merge ενώνει τα commits ενός branch μέσα σε ένα άλλο.

Υπάρχουν δύο περιπτώσεις. Το διαδραστικό παρακάτω τις δείχνει και τις δύο.

  • Fast-forward: το main δεν έχει προχωρήσει από τότε που έφτιαξες το branch. Η ετικέτα main απλώς προχωράει μπροστά. Δεν φτιάχνεται νέο commit.
  • Merge commit: και τα δύο branches έχουν προχωρήσει. Το git φτιάχνει ένα νέο commit με δύο "γονείς", που ενώνει τις δύο γραμμές.

Κανόνας ARIA

Στην ARIA, το merge στο main γίνεται στο GitHub, με ένα κουμπί στο Pull Request (κεφάλαιο 7). Τοπικά κάνεις merge μόνο από το main προς το branch σου, για να το ενημερώσεις (κεφάλαιο 8).

Συμβουλή

Μετά το merge, το branch σβήνεται αυτόματα στο GitHub. Είναι ασφαλές, γιατί τα commits του έχουν πια μπει στο main.

6. Οργάνωση της δουλειάς: Issues και Project

Αυτό το κεφάλαιο σού δείχνει πού βρίσκεις τι πρέπει να κάνεις, πριν γράψεις μια γραμμή κώδικα.

6.1Issues

Το Issue είναι μια εργασία, ένα bug ή μια ερώτηση, γραμμένη στο GitHub με δικό της αριθμό.

Κάθε Issue έχει:

  • Αριθμό, π.χ. #67. Με αυτόν το αναφέρεις παντού.
  • Τίτλο, πάντα στα αγγλικά, και περιγραφή (σε Markdown).
  • Assignee: το άτομο που το αναλαμβάνει.
  • Labels: ετικέτες, π.χ. bug, mechanical, good first issue.

Παράδειγμα ARIA: στο arm-control υπάρχει το Issue #67 "Fix IK joint limits", με assignee τη Γεωργία.

Συμβουλή

Τα Issues δεν είναι μόνο για bugs. Ένα Issue μπορεί να είναι "Σχεδίασε βάση για τον αισθητήρα", "Γράψε οδηγό για το Lidar" ή "Ποιο motor driver διαλέγουμε;".

6.2GitHub Project: ο πίνακας εργασιών

Το GitHub Project είναι ένας πίνακας που μαζεύει τα Issues σε στήλες, ανάλογα με το πού βρίσκεται η κάθε εργασία.

Οι στήλες της ARIA:

ΣτήληΤι σημαίνειΠοιος τη μετακινεί εκεί

Το "Pull Request" και το πώς κλείνει αυτόματα το Issue τα βλέπεις στο κεφάλαιο 7.

6.3Milestones

Το milestone είναι μια προθεσμία με όνομα, που μαζεύει τα Issues που πρέπει να είναι έτοιμα μέχρι τότε.

  • Έχει μια μπάρα προόδου: πόσα Issues έκλεισαν από τα συνολικά.
  • Παράδειγμα: "Arm demo: Open Day", με 5 Issues. Όταν κλείσουν 2, η μπάρα δείχνει 40%.
  • Τα milestones τα φτιάχνουν οι coordinators. Εσύ τα διαβάζεις, για να ξέρεις τι είναι επείγον.

Αναλογία

Το milestone είναι η ημερομηνία της εξεταστικής στο ημερολόγιο, μαζί με τη λίστα των κεφαλαίων που σου μένουν.

6.4Πώς ξεκινάς μια εργασία

Αυτή είναι η σειρά κάθε φορά που παίρνεις κάτι καινούριο:

  1. Άνοιξε το Project της υποομάδας σου.
  2. Διάλεξε μια κάρτα από το Να γίνει. Αν είσαι καινούριος, ψάξε το label good first issue.
  3. Βάλε τον εαυτό σου assignee στο Issue.
  4. Σύρε την κάρτα στο Σε εξέλιξη.
  5. Φτιάξε branch από ενημερωμένο main (5.6), π.χ. 67-fix-ik-joint-limits/ga.

Συμβουλή

Δουλειά χωρίς Issue δεν υπάρχει. Αν θέλεις να κάνεις κάτι που δεν έχει κάρτα, γράψε πρώτα ένα Issue ή ζήτα από τον coordinator. Έτσι κανείς δεν κάνει την ίδια δουλειά δύο φορές.

6.5Μεγάλα Issues

Αν ένα Issue είναι μεγάλο ή θα το δουλέψουν πολλά άτομα, σπάσ' το σε μικρότερα. Μέσα στο Issue, στη δεξιά στήλη, πάτα Create sub-issue.

  • Κάθε μικρό Issue έχει ένα άτομο και ένα branch.
  • Ένα καλό μικρό Issue τελειώνει σε λίγες μέρες και γίνεται ένα PR που ελέγχεται σε λίγα λεπτά.

Παράδειγμα: το Issue "Arm demo for Open Day" σπάει σε "Fix IK joint limits", "Add gripper service" και "Write demo launch file". Το καθένα το παίρνει ένα άτομο.

Συμβουλή

Ποτέ δύο άτομα στο ίδιο branch. Αν δύο άτομα χρειαστεί οπωσδήποτε να δουλέψουν στο ίδιο Issue, ο καθένας φτιάχνει το δικό του branch με τα δικά του αρχικά (π.χ. 67-…/ga και 67-…/mk), δουλεύει σε διαφορετικά αρχεία και ανοίγει δικό του PR.

Τι μπορείς να κάνεις τώρα

  • Να βρεις μια εργασία στο Project και να την αναλάβεις.
  • Να σπάσεις ένα μεγάλο Issue σε μικρότερα.
  • Να ξέρεις ποιες στήλες μετακινείς εσύ και ποια μετακινείται μόνη της.

7. Push, Pull Request και review

Αυτό το κεφάλαιο σού δείχνει πώς η δουλειά σου φεύγει από το laptop, ελέγχεται και μπαίνει στην επίσημη έκδοση του ρομπότ.

Η Γεωργία έχει δύο commits στο 67-fix-ik-joint-limits/ga. Μέχρι τώρα τα βλέπει μόνο εκείνη.

7.1Push

Το push στέλνει τα τοπικά σου commits στο GitHub.

Την πρώτη φορά για ένα νέο branch:

GitHub DesktopΓραμμή εντολών
Publish branchgit push -u origin 67-fix-ik-joint-limits/ga

Κάθε επόμενη φορά:

Το -u λέει στο git να θυμάται ότι το τοπικό 67-fix-ik-joint-limits/ga αντιστοιχεί στο 67-fix-ik-joint-limits/ga του GitHub. Γι' αυτό μετά αρκεί σκέτο git push.

Προσοχή

Το push δεν βάζει τίποτα στο main. Ανεβάζει μόνο το δικό σου branch.

Συμβουλή

Κάνε push νωρίς και συχνά. Το branch σου στο GitHub είναι το backup σου. Αν χαλάσει το laptop, η δουλειά σου είναι ασφαλής. Επίσης ο coordinator βλέπει πού βρίσκεσαι.

7.2Pull Request (PR)

Το Pull Request, ή PR, είναι ένα αίτημα στο GitHub: "ελέγξτε το branch μου και ενώστε το με το main".

Ένα PR δείχνει σε μία σελίδα:

  • Ποιο branch πάει σε ποιο (67-fix-ik-joint-limits/ga → main).
  • Το diff όλων των αλλαγών (καρτέλα Files changed).
  • Τη συζήτηση και τα σχόλια του ελέγχου.
  • Τα checks: αυτόματα τεστ που τρέχουν σε κάποια repos. Πράσινο τικ σημαίνει "πέρασαν", κόκκινο Χ "κάτι απέτυχε".

Πώς ανοίγεις PR:

  • Μετά το push, το GitHub δείχνει ένα κίτρινο banner στο repo: Compare & pull request. Πάτα το.
  • Στο GitHub Desktop: κουμπί Create Pull Request. Ανοίγει τον browser.

Προσοχή

"Pull request" δεν σημαίνει ότι τραβάς κάτι εσύ. Σημαίνει "ζητώ από την ομάδα να τραβήξει (pull) τις αλλαγές μου μέσα στο main".

Συμβουλή

Το PR δεν είναι τελικό. Αν κάνεις νέα commits και push στο ίδιο branch, το PR ενημερώνεται μόνο του.

Θέλεις γνώμη πριν τελειώσεις; Άνοιξε Draft PR (βελάκι δίπλα στο κουμπί → Create draft pull request). Σημαίνει "δεν είναι έτοιμο, ρίξτε μια ματιά".

Αναλογία

Το PR είναι η πρόταση ανακαίνισης που καταθέτεις στη διαχείριση της πολυκατοικίας πριν έρθουν οι εργάτες.

Μόλις ανοίξεις το PR, σύρε την κάρτα του Issue στη στήλη Σε review του Project.

7.4Code review και έγκριση

Το code review είναι ο έλεγχος του PR από άλλο μέλος: διαβάζει τις αλλαγές, σχολιάζει γραμμή γραμμή και στο τέλος εγκρίνει ή ζητάει αλλαγές.

Στην ARIA τον τελικό έλεγχο τον κάνει ο coordinator της υποομάδας. Μπορεί να σου απαντήσει με δύο τρόπους:

ΑπάντησηΤι σημαίνειΤι κάνεις

Request changes"Διόρθωσε αυτά πρώτα"Διορθώνεις, commit, push στο ίδιο branch, και πατάς Re-request review

Συμβουλή

Το review δεν είναι κριτική σε σένα. Είναι ποιοτικός έλεγχος για το ρομπότ. Και οι senior κάνουν λάθη, γι' αυτό ελέγχουν όλοι όλους.

Review δεν κάνουν μόνο όσοι γράφουν κώδικα. Ένας mechanical μπορεί να ελέγξει ένα BOM ή ένα PDF σχέδιο μέσα σε PR.

Καλοί τρόποι στο review:

  • Κάνε μικρά PR. Ένα PR των 50 γραμμών ελέγχεται σε 10 λεπτά. Ένα των 2.000 γραμμών δεν ελέγχεται ποτέ σωστά.
  • Εξήγησε το γιατί στην περιγραφή.
  • Απάντησε σε κάθε σχόλιο, έστω και με "Done".
  • Όταν κάνεις εσύ review, γράψε ευγενικά και συγκεκριμένα: "Εδώ μήπως θέλει έλεγχο για None;" αντί για "λάθος".
  • Μη ζητάς από φίλο να εγκρίνει "στα γρήγορα" κάτι που δεν διάβασε.

7.5Αν στείλεις κατά λάθος στο main

Στην ARIA κανείς δεν στέλνει αλλαγές κατευθείαν στο main (5.3). Αν το έκανες κατά λάθος, π.χ. με git push origin main:

  • Μην προσπαθήσεις να το διορθώσεις μόνος σου με --force. Μπορεί να σβήσεις δουλειά άλλων.
  • Πες το αμέσως στον coordinator. Θα ελέγξει την αλλαγή και, αν χρειαστεί, θα την αναιρέσει με revert (10.4).

Αν έκανες commit στο main αλλά δεν έκανες ακόμα push, δεν έχει φτάσει σε κανέναν. Δες το κεφάλαιο 10 για το πώς το μεταφέρεις σε branch.

7.6CODEOWNERS

Το CODEOWNERS είναι ένα αρχείο μέσα στο repo που λέει ποιος ελέγχει ποια αρχεία. Αν το repo σου το έχει, το GitHub προσθέτει αυτόματα τον coordinator ως reviewer σε κάθε PR. Δεν χρειάζεται να κάνεις κάτι εσύ.

7.7Merge του PR και καθάρισμα

Αυτή η ενότητα δείχνει τι γίνεται όταν το PR εγκριθεί, και πώς καθαρίζεις μετά.

Στο GitHub:

  2. Το Issue #67 κλείνει (χάρη στο Closes #67) και η κάρτα πάει στο Έτοιμο.
  3. Το branch σβήνεται αυτόματα στο GitHub. Τα commits μένουν ασφαλή μέσα στο main.

8. Μένεις ενημερωμένος: fetch, pull και conflicts

Αυτό το κεφάλαιο σού δείχνει πώς φέρνεις στον υπολογιστή σου τη δουλειά των άλλων, και τι κάνεις όταν δύο αλλαγές συγκρούονται.

Όσο η Γεωργία δούλευε, ο Μάνος έκανε merge το PR του. Το main στο GitHub προχώρησε. Το τοπικό main της Γεωργίας δεν το ξέρει.

8.1origin/main: η φωτογραφία του GitHub

Το origin/main είναι η τελευταία εικόνα που έχει ο υπολογιστής σου για το main του GitHub.

  • Το main είναι το δικό σου branch.
  • Το origin/main είναι η φωτογραφία του main στο GitHub, όπως ήταν την τελευταία φορά που κοίταξες.
  • Στο γράφημα το origin/main εμφανίζεται ως ετικέτα με περίγραμμα.

8.2Fetch

Το fetch κατεβάζει τα νέα από το GitHub (νέα commits, νέα branches) χωρίς να αλλάξει τα αρχεία σου.

terminal
git fetch
  • Ενημερώνει το origin/main.
  • Το δικό σου main και τα αρχεία στον φάκελο μένουν ίδια.
  • Στο GitHub Desktop: κουμπί Fetch origin. Αν υπάρχουν νέα, αλλάζει σε Pull origin και δείχνει πόσα commits ήρθαν.

8.3Pull

Το pull είναι fetch και μετά merge: φέρνει τα νέα και τα ενώνει με το branch όπου βρίσκεσαι.

terminal
git switch main
git pull

Στο GitHub Desktop: Fetch origin → Pull origin.

fetchpull

Κανόνας ARIA

Κάθε φορά που κάθεσαι να δουλέψεις: switch στο main και pull. Μετά φτιάχνεις ή συνεχίζεις το branch σου.

8.4Ενημέρωση του branch σου με το νέο main

Όσο το PR σου περιμένει, το main προχωράει. Κάποια στιγμή το GitHub θα γράψει στο PR: "This branch is out of date with the base branch". Αυτή η ενότητα δείχνει πώς φέρνεις το νέο main μέσα στο branch σου.

Τρόπος 1: στο GitHub. Πάτα το κουμπί Update branch μέσα στο PR. Είναι το πιο εύκολο, όταν δεν υπάρχει conflict.

Τρόπος 2: στον υπολογιστή σου.

8.5Merge conflict

Το merge conflict συμβαίνει όταν δύο branches άλλαξαν τις ίδιες γραμμές του ίδιου αρχείου με διαφορετικό τρόπο. Το git δεν ξέρει ποια εκδοχή θέλεις, οπότε σταματάει και ρωτάει εσένα.

Τι έγινε:

  • Η Γεωργία έβαλε max_velocity: 0.8 στο config/arm_params.yaml, για ασφαλή tests του IK.
  • Ο Μάνος έβαλε max_velocity: 1.2 στο ίδιο σημείο, για το demo του gripper. Το PR του μπήκε ήδη στο main.
  • Η Γεωργία κάνει git merge origin/main και βλέπει:
output
CONFLICT (content): Merge conflict in config/arm_params.yaml
Automatic merge failed; fix conflicts and then commit the result.

Τι βλέπει μέσα στο αρχείο:

yaml
arm:
<<<<<<< HEAD
  max_velocity: 0.8
=======
  max_velocity: 1.2
>>>>>>> origin/main
  gripper_force: 15

Αυτά τα σύμβολα λέγονται conflict markers:

ΣύμβολοΤι σημαίνει
<<<<<<< HEADΑπό εδώ ξεκινά η δική σου εκδοχή (current)
=======Το σύνορο ανάμεσα στις δύο εκδοχές
>>>>>>> origin/mainΕδώ τελειώνει η άλλη εκδοχή (incoming)

Πώς το λύνεις, βήμα βήμα:

  1. Άνοιξε το αρχείο σε έναν editor: Notepad, ή το VS Code αν το έχεις. Βρες τα σημάδια <<<<<<<, ======= και >>>>>>>. Στο VS Code βλέπεις πάνω από το conflict και τα κουμπιά Accept Current Change, Accept Incoming Change, Accept Both Changes.
  2. Μίλα με τον Μάνο αν δεν ξέρεις ποια τιμή είναι η σωστή. Αυτή είναι απόφαση ανθρώπων.
  3. Κράτα την τελική εκδοχή και σβήσε τις γραμμές με τα σημάδια. Βεβαιώσου ότι σβήστηκαν όλοι οι markers και αποθήκευσε.
  4. Δοκίμασε ότι ο κώδικας τρέχει.
  5. git add config/arm_params.yaml (στο Desktop: τσεκάρεις το αρχείο).
  6. git commit (το git έχει έτοιμο μήνυμα "Merge remote-tracking branch 'origin/main'…").
  7. git push. Το PR ενημερώνεται και το conflict φεύγει.

Στο GitHub Desktop, όταν υπάρχει conflict, εμφανίζεται παράθυρο με τα αρχεία που έχουν conflict. Ανοίγεις κάθε αρχείο, το διορθώνεις όπως παραπάνω και αποθηκεύεις. Όταν δεν μένει κανένα, πατάς Continue merge και μετά Push origin.

Συμβουλή

Ένα conflict δεν σημαίνει ότι χάλασες κάτι. Είναι φυσιολογικό σε κάθε ομάδα. Το git απλώς ζητάει από έναν άνθρωπο να αποφασίσει.

Αναλογία

Δύο άτομα διόρθωσαν την ίδια πρόταση σε ένα κοινό κείμενο, ο καθένας offline. Όταν συναντηθούν, κάποιος πρέπει να διαλέξει την τελική διατύπωση.

Κίνδυνος

Τα binary αρχεία (STEP, STL, PDF, εικόνες) δεν λύνονται γραμμή γραμμή. Στο conflict διαλέγεις ολόκληρο το ένα ή το άλλο αρχείο, και η δουλειά του άλλου χάνεται.

Η λύση είναι η πρόληψη: ένα άτομο ανά binary αρχείο κάθε φορά. Γράψε στο Issue "δουλεύω το gripper_v3.step" πριν ξεκινήσεις.

Διαδραστικό · M2

Λύσε το conflict

Το git δεν ξέρει ποια τιμή θέλεις. Διάλεξε εσύ, σημείωσε ότι το έλυσες και κάνε commit.

9.3Git LFS

Το Git LFS (Large File Storage) είναι ένα πρόσθετο του git για μεγάλα binary αρχεία. Κρατάει το αρχείο σε ξεχωριστή αποθήκη και βάζει στο repo ένα μικρό "σημείωμα" (pointer) που δείχνει πού είναι.

Αναλογία

Η αποθήκη στο υπόγειο της πολυκατοικίας. Το μεγάλο κουτί μένει εκεί. Στο διαμέρισμα κρατάς ένα χαρτάκι: "το κουτί είναι στην αποθήκη 12".

Τι κάνεις εσύ:

  • Μία φορά: git lfs install. Το Git for Windows το περιλαμβάνει και το GitHub Desktop το χειρίζεται μόνο του.
  • Μετά δουλεύεις κανονικά. Το repo έχει ήδη ένα αρχείο .gitattributes που λέει ότι τα *.step και *.stl πάνε στο LFS. Το έχουν στήσει οι coordinators.

Προσοχή

Το LFS δεν σημαίνει "ανέβασε ό,τι θες". Ο οργανισμός έχει όριο χώρου στο LFS. Κράτα μόνο τα exports που χρειάζονται.

Βλέπεις αρχεία STEP που ανοίγουν ως λίγες γραμμές κειμένου; Δεν έχεις εγκαταστήσει το LFS. Τρέξε git lfs install και μετά git lfs pull.

9.4Μυστικά και προσωπικά δεδομένα

Μυστικά λέμε οτιδήποτε δίνει πρόσβαση: κωδικούς, API keys, tokens, αρχεία .env. Προσωπικά δεδομένα είναι τηλέφωνα, emails, βαθμοί, βιογραφικά, λίστες υποψηφίων.

Κίνδυνος

Ποτέ σε commit. Ούτε σε private repo.

  • Το ιστορικό του git κρατάει τα πάντα για πάντα. Αν σβήσεις το αρχείο σε νέο commit, μένει στα παλιά.
  • Ένα private repo μπορεί αργότερα να μοιραστεί ή να γίνει δημόσιο.
  • Ο κωδικός του Wi-Fi του εργαστηρίου, το API key του χάρτη, τα δεδομένα της recruitment: κανένα δεν μπαίνει στο GitHub.

Αν έγινε κατά λάθος:

  3. Άλλαξε το μυστικό (νέος κωδικός, νέο key), ώστε το παλιό να μη δουλεύει πια.

10. Ουπς! Αναίρεση λαθών με ασφάλεια

Αυτό το κεφάλαιο σού δείχνει πώς διορθώνεις τα πιο συνηθισμένα λάθη, και ποιες εντολές να μην αγγίζεις.

Πώς να το διαβάσεις

Αυτό το κεφάλαιο είναι για γρήγορο διάβασμα. Δεν χρειάζεται να μάθεις τις εντολές του σε βάθος. Διάβασέ το μία φορά, για να ξέρεις ότι υπάρχουν λύσεις.

Όταν σου συμβεί κάτι, γύρνα στο 10.6: το διαδραστικό «Τι κάνω τώρα;» και ο πίνακας «τι κάνω όταν…» σού λένε τι να κάνεις σε κάθε περίπτωση.

Συμβουλή

Πρώτα, ηρεμία. Ό,τι έχει μπει σε commit σχεδόν ποτέ δεν χάνεται στ' αλήθεια. Αν δεν είσαι σίγουρος: κάνε commit στο branch σου, push, και ρώτα στο κανάλι της υποομάδας.

10.1Restore: πέτα τις αλλαγές σε ένα αρχείο

Το restore επαναφέρει ένα αρχείο στην κατάσταση του τελευταίου commit.

terminal
git restore src/ik_solver.py
  • Στο GitHub Desktop: δεξί κλικ στο αρχείο → Discard changes.
  • Προσοχή: οι αλλαγές που δεν είχαν μπει σε commit χάνονται.

Έβαλες κάτι στο staging κατά λάθος; Το βγάζεις από το staging χωρίς να χάσεις τις αλλαγές:

terminal
git restore --staged config/test_local.yaml

Στο GitHub Desktop απλώς ξετσεκάρεις το κουτάκι.

10.2Stash: το συρτάρι

Το stash βάζει τις αλλαγές που δεν έχουν μπει σε commit σε ένα προσωρινό συρτάρι, ώστε να αλλάξεις branch.

terminal
git stash        # βάζει τις αλλαγές στο συρτάρι
git switch main
# ... κάνεις ό,τι χρειάζεται ...
git switch 67-fix-ik-joint-limits/ga
git stash pop    # τις βγάζει πίσω
  • Στο GitHub Desktop: όταν αλλάζεις branch με αλλαγές, σε ρωτάει. Ή Branch → Stash all changes.

Αναλογία

Το συρτάρι κάτω από το γραφείο. Βάζεις μέσα τα χαρτιά για λίγο, καθαρίζεις το γραφείο, και μετά τα ξαναβγάζεις.

Προσοχή

Το stash δεν είναι backup. Υπάρχει μόνο στον υπολογιστή σου και ξεχνιέται εύκολα. Για κάτι που κρατάει πάνω από μια ώρα, κάνε καλύτερα commit στο branch σου.

10.3Amend: διόρθωσε το τελευταίο commit

Το amend αλλάζει το τελευταίο commit, μόνο αν δεν έχει γίνει push.

terminal
git commit --amend -m "Fix wrong sign in elbow Jacobian"
  • Ξέχασες ένα αρχείο; Κάνε git add και μετά git commit --amend --no-edit.
  • Στο GitHub Desktop: δεξί κλικ στο τελευταίο commit στο History → Amend commit….

Κίνδυνος

Αν έχεις κάνει ήδη push, μην κάνεις amend. Το amend φτιάχνει νέο commit με νέο hash. Το GitHub θα αρνηθεί το push, και η "λύση" θα ήταν force push. Κάνε απλώς ένα νέο commit με τη διόρθωση.

10.4Revert: η ασφαλής αναίρεση

Το revert φτιάχνει ένα νέο commit που κάνει ακριβώς το αντίθετο από ένα παλιό. Είναι ο σωστός τρόπος να αναιρέσεις κάτι που έχει ήδη μπει στο main.

terminal
git revert a1b2c3d
  • Στο GitHub Desktop: History → δεξί κλικ στο commit → Revert changes in commit.
  • Το revert το κάνεις σε branch και ανοίγεις PR, όπως κάθε αλλαγή.

Αναλογία

Το revert είναι μια σημείωση διόρθωσης στο βιβλίο ιστορικού: "η αλλαγή της 12/11 ακυρώνεται". Δεν σκίζεις σελίδες. Όλοι βλέπουν τι έγινε και γιατί.

Αν κάτι πήγε πολύ στραβά, οι coordinators έχουν ένα εργαλείο διάσωσης, το reflog, που θυμάται πού ήσουν πριν. Φώναξέ τους πριν δοκιμάσεις οτιδήποτε.

Για τους περίεργους: οι τρεις μορφές του reset

Το git reset μετακινεί το branch σου πίσω σε ένα παλιότερο commit. Έχει τρεις μορφές:

  • --soft: τα commits "ξεγίνονται", οι αλλαγές μένουν στο staging.
  • --mixed (η προεπιλογή): οι αλλαγές μένουν στα αρχεία, εκτός staging.
  • --hard: οι αλλαγές σβήνονται.

Α.1Fork
Το fork είναι ένα δικό σου αντίγραφο ενός ξένου repo, πάνω στο GitHub, κάτω από τον δικό σου λογαριασμό. Το χρησιμοποιείς για να προτείνεις αλλαγές σε project όπου δεν έχεις δικαίωμα εγγραφής.
  • Μέσα στην ARIA δεν κάνουμε fork. Δουλεύουμε με branches μέσα στο κοινό repo.
  • Fork θα έκανες σε ένα εξωτερικό open-source project, π.χ. έναν driver του ROS στο GitHub, για να στείλεις μια διόρθωση στους δημιουργούς του.
  • Το fork των private repos της ARIA σε προσωπικό λογαριασμό είναι συνήθως απενεργοποιημένο. Μην το δοκιμάσεις.

Α.2Worktree
Το worktree είναι ένας δεύτερος φάκελος εργασίας που ανήκει στο ίδιο repo. Σε αφήνει να έχεις ανοιχτά δύο branches ταυτόχρονα, σε δύο φακέλους.

Προχωρημένο· Α.3
Α.3Rebase
Το rebase παίρνει τα commits του branch σου και τα "ξαναπαίζει" πάνω στο πιο πρόσφατο main. Το αποτέλεσμα είναι ένα ιστορικό σε ευθεία γραμμή, χωρίς merge commits.
Γιατί στην ARIA δεν το συνιστάμε:
  • Ξαναγράφει το ιστορικό: τα commits σου γίνονται καινούρια, με νέα hashes.
  • Μετά χρειάζεται force push, που είναι κόκκινη εντολή (κεφάλαιο 10.5).
  • Τα conflicts κατά το rebase λύνονται commit προς commit και μπερδεύουν εύκολα.
  • Το όφελος, ένα πιο "όμορφο" ιστορικό, για εμάς είναι μικρό.
Ο κανόνας: για να ενημερώσεις το branch σου, χρησιμοποίησε merge ή το κουμπί Update branch (κεφάλαιο 8.4). Το rebase γενικά δεν το συνιστάμε, και ποτέ σε branch που δουλεύει και κάποιος άλλος. Μπορείς να δεις πώς δουλεύει στο διαδραστικό του κεφαλαίου 8, με τον διακόπτη "Για προχωρημένους: rebase".

Α.4Tags και Releases
Το tag είναι ένα μόνιμο όνομα για ένα συγκεκριμένο commit, π.χ. v1.0-open-day. Το Release είναι μια σελίδα στο GitHub που συνοδεύει ένα tag, με σημειώσεις και αρχεία για κατέβασμα.
Στην ARIA:
  • Σημειώνουμε την ακριβή έκδοση κώδικα και firmware που έτρεξε σε έναν διαγωνισμό ή ένα demo.
  • Σημειώνουμε ένα "κλειδωμένο" σετ σχεδίων ή BOM.
  • Ανεβάζουμε τα gerbers μιας πλακέτας (κεφάλαιο 9.2).
Τα Releases τα φτιάχνουν οι coordinators. Εσύ τα βρίσκεις στη δεξιά στήλη της αρχικής σελίδας του repo, στο Releases.

Α.5SSH keys
Τα SSH keys είναι ένας εναλλακτικός τρόπος σύνδεσης με το GitHub, με ένα ζευγάρι κλειδιών αντί για σύνδεση από τον browser. Είναι βολικά αν δουλεύεις πολύ στο terminal, π.χ. σε Linux ή WSL για το ROS.

Η γραμμή εντολών και οι εφαρμογές (GitHub Desktop, VS Code) κάνουν ακριβώς τα ίδια πράγματα, με διαφορετικό τρόπο.
  • Είναι απολύτως εντάξει να δουλεύεις μόνο με το GitHub Desktop.
  • Η γραμμή εντολών αξίζει αν είσαι στην ομάδα ROS ή σε control/perception, γιατί δουλεύεις ήδη σε Linux ή WSL.
  • Οι απαντήσεις στο internet είναι σχεδόν πάντα σε εντολές. Αν ξέρεις τη βασική αντιστοιχία (τον πίνακα του κεφαλαίου 12), τις καταλαβαίνεις.

Α.7Δουλειά ανάμεσα σε repos: το ros
Αυτή η ενότητα εξηγεί πώς συνεργάζονται οι υποομάδες όταν μια αλλαγή αφορά δύο repos.
  • Η ομάδα ros ενώνει τα κομμάτια όλων στο repo ros.
  • Κάθε υποομάδα αλλάζει μόνο το δικό της repo. Τα interfaces που δίνει σε άλλους (topics, services, μηνύματα) αλλάζουν μέσα από PR στο δικό της repo.
  • Χρειάζεσαι αλλαγή σε ξένο repo; Μίλα με τον coordinator σου. Θα το συζητήσει με τον coordinator εκείνης της υποομάδας, και η αλλαγή γίνεται από τη δική τους υποομάδα.
Παράδειγμα: η perception χρειάζεται ένα νέο topic με τις γωνίες του βραχίονα. Ο coordinator της το συζητά με τον coordinator της control, και γράφεται Issue στο arm-control: "Publish joint angles on /arm/joint_states at 50 Hz". Η control το υλοποιεί με PR στο δικό της repo, και η ομάδα ros το ενσωματώνει.

Γλωσσάρι
Το γλωσσάρι εξηγεί κάθε όρο του οδηγού σε μία γραμμή, με αλφαβητική σειρά. Οι όροι με σύμβολα και ελληνικά είναι στο τέλος.
  • 2FA (two-factor authentication): σύνδεση με κωδικό και επιπλέον έναν κωδικό μιας χρήσης από το κινητό σου.
  • Add (stage): βάζεις μια αλλαγή στο staging για το επόμενο commit.
  • Amend: διορθώνεις το τελευταίο commit, μόνο αν δεν έχει γίνει push.
  • Approval: η έγκριση ενός PR. Στην ARIA τη δίνει ο coordinator της υποομάδας.
  • Assignee: το άτομο που έχει αναλάβει ένα Issue ή ένα PR.
  • Binary αρχείο: αρχείο που δεν είναι κείμενο (STEP, STL, PDF, εικόνες). Δεν έχει diff και δεν ενώνεται γραμμή γραμμή.
  • Blame: δείχνει ποιος άλλαξε τελευταίος κάθε γραμμή ενός αρχείου. Το βρίσκεις και στο GitHub.
  • BOM (Bill of Materials): η λίστα με τα εξαρτήματα μιας κατασκευής.
  • Branch: ονομασμένη γραμμή από commits για παράλληλη δουλειά. Στην ARIA: αριθμός-τίτλος-του-issue/αρχικά.
  • Checkout: η παλιά εντολή για αλλαγή branch ή επαναφορά αρχείων. Εμείς χρησιμοποιούμε switch και restore.
  • Checks / CI: αυτόματα τεστ που τρέχουν σε ένα PR. Πράσινο τικ ή κόκκινο Χ.
  • Cherry-pick: αντιγράφεις ένα συγκεκριμένο commit σε άλλο branch. Για προχωρημένους.
  • Clone: κατεβάζεις ένα repo με όλο το ιστορικό του στον υπολογιστή σου, μία φορά.
  • Closes #N: φράση στην περιγραφή ενός PR που κλείνει αυτόματα το Issue N στο merge. Δουλεύουν και τα Fixes, Resolves.
  • CODEOWNERS: αρχείο που ορίζει ποιος ελέγχει ποια αρχεία. Το GitHub τον προσθέτει αυτόματα ως reviewer.
  • Code review: ο έλεγχος ενός PR από άλλο μέλος, με σχόλια και έγκριση.
  • Commit: μόνιμο σημείο αποθήκευσης με αλλαγές, μήνυμα, συγγραφέα, ώρα και ID.
  • Commit hash (SHA): το μοναδικό ID ενός commit, π.χ. a1b2c3d.
  • Commit message: σύντομη εξήγηση του commit, στα αγγλικά, σε προστακτική.
  • Conflict markers: οι γραμμές <<<<<<<, =======, >>>>>>> που δείχνουν τις δύο εκδοχές σε ένα conflict.
  • CONTRIBUTING.md: οι κανόνες εργασίας ενός repo, μαζί με τη λίστα αρχικών των μελών.
  • Detached HEAD: είσαι πάνω σε ένα commit και όχι σε branch. Γύρνα με git switch <branch>.
  • Diff: οι ακριβείς γραμμές που προστέθηκαν (+) και αφαιρέθηκαν (−).
  • Draft PR: PR με σήμανση "δεν είναι έτοιμο ακόμα", για γνώμη νωρίς.
  • Export (CAD): αρχείο που παράγεται από το εργαλείο CAD και το ανοίγουν όλοι (STEP, STL, PDF, BOM).
  • Fast-forward: merge όπου η ετικέτα του branch απλώς προχωράει μπροστά, χωρίς νέο commit.
  • Fetch: κατεβάζεις τα νέα από το GitHub χωρίς να αλλάξουν τα αρχεία σου.
  • Force push: αντικαθιστάς το ιστορικό του GitHub με το δικό σου. Απαγορεύεται σε κοινά branches.
  • Fork: δικό σου αντίγραφο ενός ξένου repo στο GitHub. Δεν το χρησιμοποιούμε μέσα στην ARIA.
  • git: δωρεάν πρόγραμμα στον υπολογιστή σου που κρατάει τις εκδόσεις ενός φακέλου.
  • Git LFS (Large File Storage): πρόσθετο που κρατάει μεγάλα binary αρχεία σε ξεχωριστή αποθήκη, με ένα pointer στο repo.
  • GitHub: ιστότοπος που φιλοξενεί repos του git και προσθέτει εργαλεία συνεργασίας.
  • GitHub Desktop: η επίσημη εφαρμογή με κουμπιά για git και GitHub.
  • GitHub Project: πίνακας τύπου Trello με Issues και PR. Στην ARIA: Να γίνει → Σε εξέλιξη → Σε review → Έτοιμο.
  • .git (φάκελος): ο κρυφός φάκελος με όλο το ιστορικό. Δεν τον αγγίζεις, δεν τον συγχρονίζεις.
  • .gitattributes: ρυθμίσεις ανά τύπο αρχείου. Στην ARIA λέει ποια αρχεία πάνε στο LFS.
  • .gitignore: η λίστα με τα αρχεία που το git αγνοεί.
  • HEAD: το "είσαι εδώ": το branch και το commit όπου βρίσκεσαι.
  • HTTPS / SSH: δύο τρόποι με τους οποίους ο υπολογιστής σου συνδέεται στο GitHub.
  • Issue: εργασία, bug ή ερώτηση στο GitHub, με αριθμό (π.χ. #67).
  • Label: ετικέτα σε Issue ή PR, π.χ. bug, mechanical, good first issue.
  • Local repo: το αντίγραφο του repo στον υπολογιστή σου.
  • Log / history: η λίστα ή το γράφημα των commits.
  • main: το επίσημο branch με την εγκεκριμένη έκδοση.
  • Markdown: απλή μορφοποίηση κειμένου με σύμβολα (#, -, **). Αρχεία .md.
  • Merge: ενώνεις τα commits ενός branch μέσα σε ένα άλλο.
  • Merge commit: commit με δύο γονείς, που ενώνει δύο γραμμές.
  • Merge conflict: δύο branches άλλαξαν τις ίδιες γραμμές διαφορετικά. Αποφασίζει άνθρωπος.
  • Milestone: προθεσμία με όνομα που μαζεύει Issues, με μπάρα προόδου.
  • Organization: κοινός λογαριασμός ομάδας στο GitHub. Ο δικός μας: aria-aristotle-university.
  • origin: το παρατσούκλι του remote από όπου έκανες clone, δηλαδή το GitHub.
  • origin/main: η τελευταία εικόνα που έχει ο υπολογιστής σου για το main του GitHub.
  • Personal access token (PAT): κλειδί σαν κωδικός για σύνδεση στο GitHub. Είναι μυστικό.
  • Pull: fetch και μετά merge στο branch όπου βρίσκεσαι.
  • Pull Request (PR): αίτημα να ελεγχθεί ένα branch και να ενωθεί με το main.
  • Push: στέλνεις τα τοπικά σου commits στο GitHub.
  • README.md: η αρχική σελίδα ενός repo: τι είναι και πώς το τρέχεις.
  • Rebase: ξαναπαίζεις τα commits σου πάνω σε άλλο branch. Ξαναγράφει το ιστορικό. Για προχωρημένους.
  • Reflog: το τοπικό ημερολόγιο του git για το πού ήταν το HEAD. Εργαλείο διάσωσης των coordinators.
  • Release: σελίδα στο GitHub για ένα tag, με σημειώσεις και αρχεία (π.χ. gerbers).
  • Remote: αντίγραφο του repo σε server. Το δικό μας είναι στο GitHub.
  • Repository (repo): φάκελος project με όλο το ιστορικό του.
  • Reset: γυρνάς ένα branch πίσω, ίσως σβήνοντας δουλειά. Επικίνδυνο.
  • Restore: πετάς τις αλλαγές ενός αρχείου ή το βγάζεις από το staging.
  • Revert: νέο commit που αναιρεί ένα παλιό. Ο ασφαλής τρόπος για κοινό ιστορικό.
  • Squash merge: τρόπος merge στο GitHub που ενώνει όλα τα commits ενός PR σε ένα.
  • Staging area (index): οι αλλαγές που διάλεξες για το επόμενο commit.
  • Stash: προσωρινό συρτάρι για αλλαγές που δεν έχουν μπει σε commit.
  • Status: δείχνει τι άλλαξε, τι είναι στο staging και σε ποιο branch είσαι.
  • Switch: αλλάζεις branch (git switch).
  • Tag: μόνιμο όνομα για ένα commit, π.χ. v1.0-open-day.
  • Team: ομάδα μελών του organization με πρόσβαση σε συγκεκριμένα repos.
  • Upstream: το αρχικό repo από το οποίο προήλθε ένα fork.
  • Version control: σύστημα που θυμάται κάθε έκδοση ενός project, ποιος την έκανε και γιατί.
  • Working directory / working tree: τα αρχεία που βλέπεις και αλλάζεις στον φάκελο.
  • Worktree: δεύτερος φάκελος εργασίας για το ίδιο repo, για δύο branches ανοιχτά μαζί.
